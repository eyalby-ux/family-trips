## Issue 1: `AE-003`/`AE-004` were not connected as a companion pair — possible regression against what `V53` reported as tested

Per the frozen discovery doc (`ATTRACTION_EVENT_SMART_IMPORT_DISCOVERY_V1.md`), `AE-003` (general museum entrance) and `AE-004` (paid auditorium show, same visit) are an explicit companion/duplicate-source case, same shape as Hotel's `H-001`+`H-003` pair: "Must land as two related items or one item with two attached sources — not silently merged and not silently duplicated." The implementation-time decision recorded in `MVP_DELIVERY_PLAN_CURRENT_STATE_V1.md`'s `V53` entry states this was made and tested: "`AE-003`/`AE-004` land as two separate items surfaced through the app's existing duplicate-detection dialog, not silently merged or duplicated."

Eyal's actual test: he uploaded both `AE-003` and `AE-004` and got two separate items (correct, not silently merged) — but the two items were **not connected** to each other at all — no duplicate-detection dialog, no companion/related-item link, nothing tying them together as the same visit. They landed as two fully independent, unrelated items.

Please check:
1. Does the duplicate-detection dialog mentioned in the `V53` report actually have logic that would recognize `AE-003` and `AE-004` as related (same venue, same date, different bookable event), or does "not silently merged or duplicated" in that report actually just describe the passive outcome of two unrelated extractions landing as two items — i.e. was there ever real linking logic, or did the report overstate what was verified?
2. If linking/companion-detection logic does exist in the code, trace why it didn't fire for this actual upload sequence — check how Eyal added the two documents (two separate global-Add flows vs. one attached to the other) against whatever triggers the duplicate-detection dialog, and whether same-venue-same-date-different-event is even a condition that code checks for, as opposed to only exact-duplicate detection (which `AE-003`/`AE-004` are NOT — they're companions, not duplicates, so a duplicate-detector tuned only for true duplicates would correctly not fire here, which would mean this was never actually built as a companion-linking feature despite how `V53`'s wording reads).
3. Bottom line: is this a regression (linking logic exists and broke), a gap that was never actually built (report language overstated verification), or expected behavior that the discovery doc's requirement was actually satisfied by (two separate, unrelated items, with no linking ever promised beyond "not merged")? Re-read the discovery doc's exact wording on this point before concluding — it says "must land as two related items **or** one item with two attached sources," which could be read as only requiring non-merging, not requiring an explicit visible link. Report which reading the actual implementation matches and which reading Eyal's test expected.
