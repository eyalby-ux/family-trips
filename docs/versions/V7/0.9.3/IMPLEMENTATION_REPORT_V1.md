## (A) Pantomime
- **Reuse, not duplication.** `generate_pantomime` is one more `KINDS` entry in the existing `netlify/functions/game-content.mjs` (the same file `0.9.1` chose); it goes through the **same** `generateWithRepeatGuard` / `dropRepeats` / `cleanHistory` in `_shared/game-content.mjs`, parameterized by `fields:['text']`. Tests assert there is exactly one dedup implementation, one guard, one call site, one quota consume — and none in the client. `capHistory` was generalized (a `fields` argument) rather than copied. `0.9.1` **did** expose the mechanism reusably; nothing had to be rebuilt.
- **Destination-only:** the context function returns `items:[]` whatever a caller sends; the client never sends items. Count per build: **12** (the mockup's number; the scope left it open). Exclusion list on every call incl. the top-up, normalized dedup, one bounded top-up, ship short — all tested with a mocked AI.
- **Actor pick (concrete examples from the tests):** with participants a, b, c a draw of "a" right after "a" is re-rolled to "b"; over a 6-round game the actors were `a c b c b a`; with two participants `a b a b a b a b a b` (a strict alternation). **Implementation note:** "re-roll once" is implemented as "pick among the OTHERS" — a plain second random draw could still repeat with two participants and would not alternate strictly, which the scope says it must. Live on `qa`: a 12-round game with five participants — the same person never performed two rounds in a row.
- **Round flow (live-verified, a full 12-round game on `qa`):** look-away screen naming the actor ("מעבירים את הטלפון ל… — כל השאר, תביטו לכיוון אחר!", an "נבחר/ה אוטומטית להציג" badge; the phrase is NOT on it) → "הצג את הביטוי" → private reveal (no timer) → "הצגתי, עברו לניחוש" → tap who guessed (the actor is not offered) or **"דילוג — לא ניחשו"** → next. Phrases were kid-friendly Argentina scenes ("מטפסים על האובליסק", "פינגווין מטייל בפטגוניה"…). Cloud save of the deck verified (survives a full reload).
- **End:** tally with medals, then the shared winner animation **twice** (live: confetti, then stars, both naming the winner, big), then "שחקו שוב" (no AI) / "בנה פנטומימה מחדש". Reopening the finished game never replays it.
- **State shape — one deviation:** `pantomimeState = {order, position, scores, lastActorId}` as scoped **plus `currentActorId` and `actorPosition`** (who performs the open round, and for which position), so that closing and reopening the app mid-round keeps the same actor instead of picking again. Needs 2+ active participants to start (a hint says so). New id → no backfill (tested: pushed into a trip that lacks it, a built one is untouched, never pushed twice, per-trip copies).

## (B) מזכיר לי
- **Instructions text:** the kickoff's draft is used **verbatim** (confirmed as-is; it reads well). Not tagged interactive.
- **Implementation choice — bespoke card, not the `interactive` plumbing:** the game keeps the plain instructions page and the generic "התחל פעילות" (like `סיפור בהמשכים`), and gains one "התחלה חכמה" card on that page. The chain is free-form — nothing to play back or track — so the start/continue/play-screen machinery would add nothing.
- **Built as scoped:** the family picks a mode first (two tiles, the same component as Bingo's place picker); the mode is remembered (`remindMeMode`); **only that mode is generated, one call, never both** (schema and extraction enforce it even if the model adds the other field); **switching back to a mode shows its cached suggestion with no call** (tested, and live: after a word call and a song call, two switches back made 0 further requests); an explicit "החלפת ההצעה" is a fresh call for the same mode only and the other mode is untouched; failure changes nothing. History: 10 per mode, sent only for that mode, prompt-only (no server dedup). Gated on a destination (visible, disabled, with the hint). One call = one daily quota call; a family trying both modes spends two (as the scope says).
- **The real-song wording (the part doing real work):** the system prompt says — in capitals — *HARD REQUIREMENT: the song must be real*; *never invent a song title; never guess an artist*; name a song **only if genuinely confident that exactly this title by exactly this artist exists, otherwise choose a different song you ARE sure about**; *prefer very famous, widely known songs over obscure ones (a famous song is far less likely to be a fabrication)*; *never pair a title with another artist's name*; lean to the destination's country / culture / language; family-friendly; never repeat the exclusion list. **Honest limit:** this lowers the risk of a fabricated song or a wrong artist, it cannot remove it — there is no external check or curated list (both declined). Live example on the QA trip (Argentina): word "טנגו", song **"Color Esperanza" — Diego Torres**, which is a real, well-known Argentine song.
- **My choice on the open question (disclosure):** a small muted line **under a song suggestion only**: "ההצעה נוצרת בבינה מלאכותית — כדאי לוודא שהשיר קיים לפני שמשמיעים אותו." Cheap, honest, and not shown for words. Tell me if the Product Owner prefers none.

## (C) New-user onboarding
- **Source check that differs from the kickoff:** `empty()` is not *only* reachable with zero trips — it is what every tab (Today, Timeline, Trip Center, Packing, Settings) shows when `state.trip` is null, so a returning user with trips who taps a tab before opening one lands on it. So the two-path screen is gated explicitly on **no trip open AND `myTrips.length===0`** (`showsOnboarding`, tested incl. the returning-user case); everyone else keeps today's one-button screen. `boot()` already sends a user with trips to the "הטיולים שלי" view, so a first-ever launch is the real case. No "has ever had a trip" flag was invented.
- **Screen:** the approved copy, two cards built by the **same** card component (so equal weight, and **always the same height** — fixed after I measured 111px vs 92px), "או" between them, the QR/manual hint. "העלאת המסמך הראשון" is today's `create` action (the intake modal) — untouched, nothing pre-filled from the document (my choice for that open question: no pre-fill, no behaviour change). "הוספת תאריכים ויעד" opens the inline form (destination, start, end, the approved hint, "יצירת הטיול", and the ghost "דילוג — אעדכן בהמשך").
- **Submit:** `ensureTrip({name:'טיול ל<country>',startDate,endDate})` (dates sanitized by the existing `sanitizeTripDates`; an end before the start is pulled to the start, the settings rule) and the country into `destinationCountries` — the same field the יעדים form writes — then `save()`. A missing destination creates nothing.
- **My choice for partial abandonment:** the back arrow and "דילוג" both return to the two-choice screen and create **nothing** (typed values are not kept), the same as every other cancel-mid-form path.
- **Not exercised live:** it needs a Google account that has never had a trip (the QA account has two). Verified by tests and by rendering the screen's exact markup in the app's own CSS at 360px (cards 286×111 each, no overflow). **Please check it once with a brand-new account.**

## Found while testing — a latent sync bug, fixed (`3d589a9`) — please read
Building a Pantomime deck on `qa` showed "שמירת השינויים בענן נכשלה" and the console said *No document to update: …/games/game-pantomime*. **Cause:** `mergeRemoteState()` cloned the state into the sync baseline **after** `normalizeOperationalState()` had pushed the missing built-in games into it, so a game new to the trip looked "already synced": it was never created in Firestore and its first edit failed (the deck lived only on that device). The same baseline also made a game the normalizer **removed** look already deleted. This could only show up for a brand-new built-in id, which `0.9.3` is the first release to add (`0.9.1` / `0.9.2` only changed existing ids) — so Production today is not failing, but **`0.9.3` would have shipped Pantomime and מזכיר לי unable to save to the cloud**. **Fix:** `syncBaseline(remoteGames, normalizedState)` — a game that exists remotely keeps its normalized version, a game the normalizer added is left out (created on the next save), a game it removed keeps its remote record (deleted on the next save); the remote games are captured **before** the normalizer edits the shared array in place. Tested with the real `diffById` (new games created, the old one deleted, no update of a missing document, no spurious writes on a complete trip, the old behaviour reproduced). Verified live: the deck builds, no error, and survives a reload. **Side effect to know:** the `ציד תמונות` (0.9.2) and `מי אני?` (0.9.1) documents that those releases only hid locally are now **deleted from Firestore** the first time each trip saves on `0.9.3`; my earlier reports said that "goes with the next sync", which was **not true until this fix**.
