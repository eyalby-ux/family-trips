# FamilyTrips `0.7.3` — Design: sync engine, conflict resolution, offline queueing, two-device collaboration

**Document revision:** `V1`
**Candidate:** `0.7.3` (Alpha 0.7's third candidate), `version/V7`
**Status:** Design document only. No `0.7.3` feature code, no deployment. Per `MVP_DELIVERY_PLAN_CURRENT_STATE.md` `V102`, implementation does not begin until the Product Owner reviews this.
**Date:** 2026-09-15

## 0. Two urgent findings from current-state verification — read this first

The design-request explicitly asked to verify `0.7.2`'s real sync behavior directly against the code rather than assume. Doing that surfaced two concrete, severe gaps already shipped and live in Production, not hypothetical `0.7.3` risks. Both are stated here before anything else because they matter for how the rest of this document should be read, and because the standing project discipline is to report a finding like this directly rather than fold it quietly into a future design.

### 0.1 An offline edit can be silently and completely lost on reload

`save()` (`src/v5-app.js`) serializes every write through one chained promise, `saveInFlight`, and each link in that chain does `await syncTripState(...)`, which itself does `await batch.commit()`. The Firestore SDK's own `WriteBatch.commit()` is explicitly documented (`node_modules/@firebase/firestore/dist/index.d.ts`, verified directly): *"it won't resolve while you're offline."* So while offline, the **first** queued `save()` reaches `commit()` and (per Firestore's own persistence model) that write is journaled into Firestore's durable, IndexedDB-backed mutation queue immediately when `commit()` is called — independent of when the returned Promise resolves. That part is safe.

The problem is everything **after** the first offline edit. Because `saveInFlight` chains the *whole* async function — including the unresolved `commit()` — behind a `.then()`, every subsequent `save()` call made while still offline sits queued behind that pending Promise and **never even reaches its own `batch.commit()` call** until the first one's Promise resolves, which requires reconnecting. If the tab is closed or the app is reloaded while offline with more than one edit made, only the first edit was ever actually handed to Firestore's durable queue — every edit after it existed only as an in-memory JavaScript object (the captured `snapshotForThisSave` closure and the live `state` object itself), and reload discards all in-memory state unconditionally. There is no other durable local copy: `0.7.2` removed the synchronous `localStorage` write entirely; the only `localStorage` keys still written are `ACTIVE_TRIP_KEY` (which Trip is open) and the legacy, read-only migration blob (confirmed by a full grep of `localStorage.setItem`/`getItem` in `src/v5-app.js` — nothing else exists).

This is a direct violation of the frozen "no silent data loss" offline invariant (`ARCHITECTURE_CURRENT_STATE.md`), already shipped in `0.7.2`, not a `0.7.3` risk to avoid introducing. See §3 for the recommended fix and §7 for whether it should wait for `0.7.3` or be corrected sooner.

### 0.2 A live remote update can silently wipe an open, unsubmitted form

`render()` does one unconditional `document.querySelector('#app').innerHTML = ...` on every call — a full replacement of the entire app DOM. `openTrip()`'s `subscribeToTrip` callback calls `render()` on *every* remote snapshot change, including this device's own write echoing back, another Editor's concurrent edit, or another browser tab on the same device. If the user has an edit form open (a Trip's name, an Item's fields, a Task) with unsaved keystrokes in progress when any such update arrives, the entire form is destroyed and replaced from the fresh remote state — the in-progress text is gone, with no warning, indistinguishable to the user from data loss because it *is* data loss (of an edit they hadn't submitted yet).

This is a real risk `0.7.2`'s single-device acceptance testing was very unlikely to catch (the window is short — it only matters while a form is genuinely open and another write lands in that exact interval) but a two-device sync engine makes routine, since remote updates are now expected to arrive continuously while the app is in normal use. See §2.3 for the recommended fix.

## 1. Current-state verification

### 1.1 What `0.7.2` actually built for real-time sync

Confirmed directly (`src/cloud-store.js`): `subscribeToTrip(tripId, onUpdate, onError)` attaches a real Firestore `onSnapshot` listener to the Trip document itself, plus one more `onSnapshot` listener per subcollection in `SYNCED_COLLECTIONS` (`items`, `sources`, `suggestions`, `rejectedSuggestions`, `tasks`, `packingLists`, `shopping`, `locationRecords`, `games` — 9 collections, 10 listeners total including the Trip document). Every listener has a real `error` callback (added during `0.7.2`'s own acceptance-cycle correction, not present in `0.7.2`'s first version). This *is* already real-time, two-way sync for reads: any write from any device to any of these paths triggers every other open listener on that same Trip within Firestore's own normal propagation latency (typically well under a second on a live connection).

### 1.2 What happens when a remote change arrives during local activity

Two distinct answers, both already covered above and both real gaps:
- If the user has no form open, a remote update just re-renders the current view with fresh data — this already works correctly and needs no `0.7.3` change.
- If the user has a form open with unsaved input, §0.2 applies: the update destroys it.

Separately, if the user has made a local edit that hasn't finished its Firestore round-trip, §0.1 applies to what happens if the app is closed/reloaded before that round-trip completes.

### 1.3 `0.7.2`'s own forward note, confirmed

`0.7.2`'s design document speculated `0.7.3` would "likely" build substantially on the same listeners rather than a separate mechanism. Confirmed correct for the *read* path (§1.1) — no new listener infrastructure is needed. Not confirmed, and in fact the opposite, for the *write* path — `0.7.2` never built anything for conflict resolution or offline queueing durability, and the one thing it did build for the write path (§0.1's serialization) has a real gap that needs fixing, not just extending.

## 2. Conflict resolution / merge strategy

### 2.1 The granularity that already exists, for free

`syncTripState`'s diff (`diffById`, `src/operational-data.js`) already operates at **per-record** granularity — one Firestore document per Item, per Task, per packing list, etc., not one big Trip blob. This means two devices editing *different* records (device A edits Item X, device B edits Task Y) already merge with zero additional work: they're literally different Firestore documents, and Firestore's own per-document write ordering handles this correctly today. This is worth stating plainly since it's the majority of real concurrent-editing scenarios for a family trip-planning app — most edits touch different items.

### 2.2 The real gap: same-record, different-field edits

The diff currently writes a **whole changed record** (`batch.set(ref, record, {merge:false})`) whenever *any* field of that record differs from the last-synced snapshot — not a field-level patch. Concretely: if device A (offline) changes an Item's `notes` field, and device B (online, concurrently) changes the *same Item's* `title` field, then when A reconnects and its queued write finally lands, A's full-record overwrite (carrying A's old `title` alongside A's new `notes`) silently reverts B's title change — even though A and B never touched the same field. This is exactly the "silent loss" failure mode the design-request asked to be named explicitly rather than glossed over.

**Recommendation: switch record writes from whole-document `set()` to field-level `updateDoc()` with only the fields that actually changed.** `diffById` needs to compute and return a field-level delta per changed record (which fields differ, not just "this record differs"), and `syncTripState` writes only those fields via `updateDoc(ref, {...changedFields})` instead of replacing the whole document. This closes the cross-field silent-loss case entirely — two devices editing different fields of the same record, even across an offline/reconnect boundary, both survive.

**What this does not solve, stated plainly rather than glossed over:** two devices editing the *exact same field* of the exact same record concurrently is still last-write-wins — whichever write reaches the Firestore server last overwrites the other's value for that field, with no merge possible (there is no meaningful way to "merge" two different values typed into the same text field without building real operational-transform/CRDT tooling, which is far beyond what this app's actual usage pattern — a handful of family members editing trip plans, not a real-time collaborative document editor — justifies). **Recommendation:** accept last-write-wins at the single-field granularity as the final answer, but add a lightweight `updatedAt`/`updatedByUid` pair to each record (cheap, a few bytes) so that if this genuinely rare case ever happens, it is at least attributable after the fact rather than a complete mystery — not surfaced to the user as an interactive conflict-resolution UI, which would be real added complexity for a failure mode this narrow and this infrequent for the app's actual usage pattern.

### 2.3 The open-form overwrite (§0.2) needs its own fix, separate from write-path merging

This is a render-path problem, not a data-merge problem — the underlying data was never actually lost in Firestore, only the user's *not-yet-submitted* local draft was destroyed by a full re-render. **Recommendation:** `render()` should not blindly replace a form the user is actively editing. The minimal, low-risk version of this: track whether a form-carrying modal (`state.modal` is set to an edit/create type) is currently open, and while it is, skip the full-DOM-replacement path for the parts of the tree containing that open form — either by not re-rendering at all while a form is open (simplest: buffer the incoming remote state, apply it only once the form closes) or by re-rendering everything *except* the live form subtree. Given this app's existing rendering model (one `innerHTML` replacement, no virtual-DOM diffing framework), **buffering remote updates while a form is open and applying them the moment it closes is the simpler, lower-risk option** — it doesn't require introducing partial-DOM-patching logic into a codebase that has never had any, and the cost (a remote update the user sees a moment later than otherwise) is minor compared to the alternative (silently destroying their in-progress edit).

## 3. Offline write queueing

### 3.1 What the environment actually gives us (verified, not assumed)

Firestore's own persistent local cache is already enabled (`src/firebase.js`, `initializeFirestore` with `persistentLocalCache`/`persistentSingleTabManager`, added in `0.7.2`). Per Firestore's documented behavior and the SDK's own type comments (§0.1), a write call — once actually issued — is journaled into this durable, IndexedDB-backed queue immediately, independent of network state or when its Promise resolves; the SDK itself replays this queue automatically on reconnect, in order, with no application code needed to rebuild that mechanism. **This means `0.7.3` does not need to build its own offline write queue from scratch** — the gap in §0.1 is not "Firestore fails to queue writes offline," it's "this app's own serialization logic (`saveInFlight`) prevents a write from ever being issued to that queue in the first place, for every edit after the first one made while offline."

### 3.2 Recommended fix

Decouple *diff computation* (which must stay serialized, to avoid two concurrent edits computing a diff against the same stale `lastSyncedSnapshot` and clobbering each other) from *waiting for server acknowledgment* (which must not block the next edit from being issued). Concretely: `save()` should synchronously compute the diff against the current `lastSyncedSnapshot`, immediately call `batch.commit()` (handing it to Firestore's own durable queue right away, regardless of whether the previous call's Promise has resolved yet), and only serialize the narrow step of updating `lastSyncedSnapshot` itself once each write's Promise does resolve, in order. This is a bounded, well-understood change to `save()`'s existing serialization, not a new subsystem.

**This recommendation rests on Firestore's documented persistence model, not something verifiable by direct testing from this environment** — no Firestore emulator is available here (an established limitation throughout this project), and genuinely offline conditions against a real Firestore session can't be simulated from this sandbox. It needs to be empirically confirmed during implementation and, especially, during the two-device acceptance session (§5, Test F) — specifically: make two offline edits, reload while still offline, reconnect, and confirm both survive.

### 3.3 What happens if the app is closed with writes still in Firestore's own local queue (not yet server-acknowledged)

This is the part Firestore's persistence layer is designed for and should already handle correctly once §3.2's fix stops the queue from stalling: a write journaled into Firestore's IndexedDB-backed queue survives a reload/close, because IndexedDB itself is durable, unlike this app's own in-memory `state`/`saveInFlight`. This should be explicitly verified during acceptance testing (Test F) rather than assumed correct just because it's documented behavior.

## 4. Sync status visibility — a user-experience question, not an implementation detail

Today the app already has one minimal offline signal: a `.offline` banner in `render()`'s own shell markup, shown whenever `!navigator.onLine`, with no equivalent signal for "online, but a local edit hasn't finished syncing yet" or "a write failed." Three real options, with their tradeoffs stated plainly rather than a default silently picked:

1. **No indicator beyond the existing offline banner (status quo).** Simplest, zero new UI. Tradeoff: the user has no way to know whether their last edit actually reached the server, especially right after reconnecting — they'd have to trust it silently worked, which is a weaker guarantee than what `0.7.2`'s local-only synchronous save gave them before (that one was inherently instant and visible-by-absence-of-error).
2. **A minimal "pending sync" indicator, extending the existing offline banner's own pattern.** When there are local writes not yet confirmed synced (`saveInFlight` still has unresolved links), show a small, unobtrusive signal — extending the same banner already used for offline (e.g., "שינויים ממתינים לסנכרון" instead of/alongside the offline text once back online with a backlog). Low implementation cost (the information already exists in `saveInFlight`'s own state), consistent with the one pattern this app already has for this kind of signal. **This is the recommended default** — it directly answers "did my edit actually save" without introducing a genuinely new UI pattern.
3. **A richer sync-status surface** (a dedicated indicator per item/section showing its own sync state, or a toast on every successful/failed sync). More visibility, but real added UI surface and complexity for a household trip-planning app where the collaborators are a handful of family members, not a team needing granular audit visibility into every write. Not recommended as the `0.7.3` default; worth reconsidering only if acceptance testing shows option 2 isn't enough.

**This is presented as a recommendation, not a decision** — per the explicit instruction, this is exactly the kind of choice that should be confirmed by the Product Owner, not settled unilaterally.

## 5. Two-device acceptance testing protocol

All tests run against the dedicated QA Test Trip (§6), with Account A (Owner) and Account B (Editor) on two genuinely separate devices/browsers, both already established from `0.7.2`'s own testing.

- **Test A — baseline near-real-time.** Both online. A edits an item. Confirm B sees the change without a manual refresh, within a stated window (the design recommends this window be whatever Firestore's own normal propagation latency is on a live connection — sub-second to a few seconds — confirmed empirically during this test, not asserted here as a number this document can't verify from this environment).
- **Test B — offline edit, single device, then reconnect.** A goes offline, edits an item. Confirm B (online) does not see the change yet. A reconnects. Confirm B then sees it within the same window as Test A.
- **Test C — concurrent edits, different records.** Both A and B go offline, each edits a *different* item, both reconnect around the same time. Confirm both edits survive on both devices (validates §2.1's already-correct behavior under real offline/reconnect conditions, not just in theory).
- **Test D — concurrent edits, same record, different fields.** Both offline, both edit *different fields* of the *same* item, both reconnect. Confirm both field changes survive on both devices (validates §2.2's field-level-merge fix specifically).
- **Test E — concurrent edits, same record, same field.** Both offline, both edit the *same field* of the same item with different values, both reconnect. Confirm the app does not crash or corrupt data — one value wins (last-write-wins, by design, per §2.2) — and this is treated as an expected, non-blocking result, not a defect, unless the outcome is genuinely inconsistent between the two devices (both must converge to the *same* final value, even if it isn't "correct" from either user's perspective).
- **Test F — reload while offline with pending edits (validates §0.1/§3.2's fix directly).** A goes offline, makes two or more edits in sequence, then closes and reopens the app/tab *while still offline*, then reconnects. Confirm all edits survive and reach B.
- **Test G — open form survives a concurrent remote update (validates §2.3's fix directly).** A opens an edit form (e.g., editing an Item) and types into a field without submitting. While that form is open, B makes an unrelated edit that syncs to A. Confirm A's in-progress, unsubmitted form is not wiped — either the update is visibly deferred until the form closes, or some other explicit, intentional behavior occurs, but not silent data loss.
- **Sync status visibility check.** Confirm whatever is built for §4 actually reflects true state through each of the above — in particular, that it shows "pending" during Test B/F's offline window and clears once reconnection completes.

This is deliberately specific enough to write the real `EXECUTABLE_TEST_SESSION_V1.md` from directly, not something to be improvised during the session itself, per the design-request's own instruction.

## 6. Shared-backend testing implications

**Recommendation: the existing "QA Test Trip" convention remains sufficient for two-device testing — no separate `qa` Firebase project is needed for this reason.** The concern the QA Test Trip convention was built to address (`VERSION_PACKAGE_AUTHORING_STANDARD_V54`) was acceptance testing polluting the Product Owner's *real, non-test* Trips with test data, because `qa` and Production share one backend. That concern is orthogonal to how many devices are testing at once — two-device testing is, by definition, two sessions (Owner + Editor) operating concurrently on *one shared Trip*, which is exactly what the QA Test Trip already is. Using it for two-device sync testing doesn't introduce any new commingling risk beyond what single-device testing already had, and a separate Firebase project would add real, ongoing overhead (a second set of security rules and `config/appInvitations` to keep in sync with the real ones, a second Storage bucket, a second CORS configuration) to solve a problem this candidate doesn't actually have. If the concern resurfaces, it will more likely be about test *volume* (many rapid test writes against one Trip, which the field-level-merge and offline-queueing fixes above both write more frequently than `0.7.2`'s whole-record writes did) than about device count — worth revisiting only if that becomes a real friction point in practice, not preemptively here.

## 7. Effort/risk assessment

**Recommendation: keep `0.7.3` as one candidate**, for the same reason `0.7.2` stayed one candidate — a sync engine without offline-durability correctness is actively dangerous (silent data loss is worse than no sync at all), and offline-durability correctness without any status visibility leaves the user unable to tell whether it's working. They're not independently shippable in a way that makes sense to split.

**One explicit exception, flagged rather than decided here: §0.1's offline-data-loss bug is already live in Production today, in `0.7.2`, not a `0.7.3` risk to avoid introducing.** Whether this warrants a fast, narrow `0.7.2.x`-style correction ahead of `0.7.3`'s own full timeline, or gets folded into `0.7.3`'s own implementation (since §3.2's fix is the same fix either way), is a real scheduling decision this document is surfacing rather than making. The case for a fast correction: it's a genuine silent-data-loss bug in a live product, matching the severity class this project has always treated urgently (e.g., `0.7.2`'s own mid-cycle corrections). The case against: the fix (§3.2) is small and well-understood, but validating it properly really wants the same two-device, genuinely-offline testing conditions `0.7.3`'s own acceptance session is already being built for — a rushed single-device `0.7.2.x` correction risks a false sense of confidence without the real test coverage this exact bug needs to be trusted.

**Sizing**: `§2.2` (field-level diff/merge) touches `diffById` (`src/operational-data.js`) and `syncTripState` (`src/cloud-store.js`) — contained, not a rewrite. `§2.3` (open-form buffering) touches `openTrip`'s subscription callback and possibly `render()`'s own entry point — contained. `§3.2` (save() decoupling) touches `save()`'s own serialization — contained, and shared with the `0.7.2.x`-or-`0.7.3` scheduling question above. `§4` (sync status UI) is small, additive UI, no architectural risk. None of this requires new infrastructure the way `0.7.2` did (no new datastore, no new security-rules model) — this is a correctness and UX pass on top of what `0.7.2` already built, not a second foundational build.

**Risk flags**:
- No Firestore emulator is available in this environment for any of these fixes — every claim about offline/reconnect behavior in this document is reasoned from Firestore's documented persistence model and the installed SDK's own type comments, not empirically verified here. The two-device acceptance session (§5) is where these claims actually get tested for the first time.
- Field-level `updateDoc()` writes (§2.2) are a real behavior change from the current whole-record `set()` writes — worth a specific regression check that deleting a field from a record (not just changing its value) still works correctly under `updateDoc()`'s own semantics (a `set(...,{merge:true})`-style field write does not automatically remove a field that's been deleted client-side unless explicitly told to, via Firestore's `deleteField()` sentinel) — flagged here as an implementation detail to get right, not assumed correct by default.
